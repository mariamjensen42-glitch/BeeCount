# 退款/退货记账（红字冲销）与报销标记

## 背景

用户在日常记账中需要两种能力：一是收到退款/退货时记录这笔冲销（而不是当作收入），二是记录某笔支出是否已报销（如因公垫付后被公司打款）。此前 `EntryType` 只有 `EXPENSE` / `INCOME` / `NEUTRAL`，微信账单导入的退款统一记为 `NEUTRAL`（不参与任何统计），而手动/AI/OCR 记账无法创建退款记录，也没有报销标记的概念。

## 决策

### 新增 `EntryType.REFUND`（红字冲销）

- 账目类型新增第四类 `REFUND`：真实入库、出现在账本页。
- **统计口径**：任何支出相关统计都按「支出 − 退款（同类别/同日期的退款冲减）」的净额计算，退款金额冲减后不为负（下限 0.0）。今日合计、日历页金额与绿点、图表页分类排行/每日支出/年度趋势/热力图、预算消费、桌面小组件、账本页筛选合计全部采用此口径。
- **入口**：手动/AI/OCR 记账均可创建退款记录；AI 解析的输出格式新增 `refund` 类型与 `is_refund` 字段；微信账单导入中的退款行（状态或类型含「退款」）也从 `NEUTRAL` 改为 `REFUND`，类别按关键词映射到原支出类别。
- **类别**：退款记录使用原消费的支出类别名（快照），统计时按类别名精确匹配冲减。

### 新增 `isReimbursed` 报销标记

- `Entry` / `EntryEntity` 新增 `isReimbursed: Boolean` 字段，仅对支出有效。
- 收入/退款/中性记录恒为 `false`（写入时强制归一），UI 不展示该标记。
- AI 解析的输出格式新增 `is_reimbursed` 字段（用户明确说「这笔已报销」时 true）。
- 标记不自动生成报销收入记录：报销款到账由用户自行记账，可选用预置「报销」收入类别。

### 数据库迁移

- Room 数据库从 v9 升到 v10：`entries` 表新增 `isReimbursed INTEGER NOT NULL DEFAULT 0` 列。无损迁移，仅加列，不动已有数据。
- `EntryType` 新增 `REFUND` 不影响 Room 列类型（enum 以 name 字符串存储），已有数据库中不存在 `REFUND` 值，迁移无需改写旧数据。

### UI

- 编辑账目弹层新增「退款」类型 chip 与报销标记（仅支出显示）。
- 账本页/日历页/今日列表中的退款显示为 `-¥xx（退）`，使用主色而非支出红；已报销支出显示「已报销」标签。
- 账本页综合筛选面板新增「退款」类型 chip。
- 微信导入确认层分别报告「退款 N 笔」与「中性 N 笔」。
- CSV 导出新增「退款」类型。

## 拒绝的方案

- **退款续用 `NEUTRAL`**：中性记录不参与任何统计，无法体现「冲减支出」的会计语义。
- **退款作为负数金额的支出**：否定了 `EntryType` 的完备性，且与现有统计 SQL/领域模型的类型判断分散。
- **退款必须关联原支出记录**：会计上「红字冲销」按分类/日期冲减即可表达语义，关联原记录带来额外的引用完整性、跨账本聚合与撤销复杂度，对个人记账收益有限。

## 影响

- 统计聚合、DAO SQL、预算消费、widget、CSV 导出等所有支出相关口径都需要「支出 − 退款」。
- AI 系统 Prompt 与 `AiEntryJsonDecoder` 增加 `refund` / `is_reimbursed` 字段。
- 微信账单导入的退款行由 `NEUTRAL` 改为 `REFUND`，导入确认层报告退款笔数。
- 相关单测（`AnalyticsAggregatorTest`、`EntryIntakeTest`、`WeChatBillClassifierTest`）补充退款/报销断言。
